# Full-fidelity LLM bodies for the Forge 1.20.1 server

Research date: 2026-11-20. Web/source inspection only: no installations, game launches, SSH, or server access. Server/host details and existing MCP behavior below are supplied task context, not newly measured. Links are sources fetched in this research session. **UNVERIFIED** means the particular compatibility, API, or performance claim was not established; a project advertising support does not establish compatibility with this 160-mod pack. Effort and resource figures are explicitly engineering estimates, not benchmarks.

**Recommendation:** one real Forge 1.20.1 client per resident, with the exact gameplay modpack, real rendering on a virtual display, a small authenticated in-client API, and the existing MCP runtime adapted to drive it. Start from the MIT-licensed Synapse client bridge as reusable source, not as a proven drop-in multiplayer product. Add Baritone for bounded navigation/mining. The important limitation is that running every mod makes its client behavior available, but does **not** automatically turn arbitrary custom GUIs into semantic tools.

## 1. Headless real clients

### HeadlessMC: launcher support is not automation-mod support

- [HeadlessMC launch documentation](https://headlesshq.github.io/headlessmc/launch/) supports Forge, Fabric, and NeoForge launch targets, installed version JSONs, separate game directories/profiles, and modpacks. The launcher is not tied to one Minecraft version. **Forge 1.20.1 is a plausible launch target, but this pack's successful launch is UNVERIFIED.** Use the exact Forge build/configs, rather than silently resolving a different build.
- Its [command reference](https://headlesshq.github.io/headlessmc/commands/) exposes `--offline`, `--server`, JVM arguments, resolution, and `--headless`/`-lwjgl`. However, its [README](https://raw.githubusercontent.com/headlesshq/headlessmc/main/README.md) explicitly says accounts are validated and offline accounts are only for headless CI/CD. **Do not promise that HeadlessMC permits arbitrary offline identities in a normally rendered virtual-display session.** The server being offline-mode does not remove a launcher's own account policy.
- `--headless` is **LWJGL stubbing**, not invisible normal rendering. The [LWJGL module README](https://raw.githubusercontent.com/headlesshq/headlessmc/main/headlessmc-lwjgl/README.md) describes replacing LWJGL method bodies with redirected/default-return behavior. Its compatibility with this pack's graphics/native calls is **UNVERIFIED**. [HMC-Specifics](https://github.com/headlesshq/hmc-specifics) explicitly says screenshots require actual rendering and are disabled in the stubbed mode. Therefore stubbing is the wrong first choice for a goal that includes screenshots and arbitrary mod screens.
- [HMC-Specifics](https://github.com/headlesshq/hmc-specifics), MIT, provides GUI listing/clicks/text, server connect/disconnect, chat, respawn, rendered-text capture, metrics, screenshots, and custom command hooks. **Its current support table does not list 1.20.1:** it lists 1.20.6, 1.19.4, 1.18.2 and other versions, with Forge/Fabric builds. Do not install a 1.20.6 jar on 1.20.1 or count these hooks as already available there. A 1.20.1 port would be additional work; an independent Forge API bridge avoids that dependency.

### Resource budget and safe trimming

**No credible measurement of this exact pack was obtained. “160 mods” alone does not determine typical RAM or CPU.** Initial **UNVERIFIED planning estimate per bot**: 4–6 GiB Java heap, roughly 6–9 GiB total process/container RAM including native allocations; allow 2–4 logical CPUs during load/pathfinding/software-render bursts. These are capacity allowances, not claims that the client constantly consumes those cores or will fit. Start around 640×360, 10–20 rendered FPS and 4–6 chunk render distance, then measure RSS, startup peak, frame/tick time and server TPS before adding another bot. Heap is not an RSS limit. Low FPS must not accidentally throttle simulation/input execution.

For the supplied machines, start **one bot on bazzite**, not beside the already memory-tight 24G server on pop-os. Containerize the client/bridge with a separate writable game directory and identity per bot. Do not infer safe bot counts from nominal RAM alone.

Trimming rules:

- Disable shaders/high-resolution resource packs and unnecessary visual effects first; mute sound or use a nonphysical audio sink rather than deleting gameplay mods. These are **proposed configuration changes**, not a verified compatibility list.
- [Distant Horizons metadata](https://api.modrinth.com/v2/project/distanthorizons) lists MC 1.20.1, explains Forge/Fabric support for 1.20.4 and older, and marks client/server installation optional. It is a sensible removal candidate for an agent client. **Removal with the exact installed DH build and dependent mods is UNVERIFIED**; keep it if the pack's dependencies require it.
- Do not remove mods merely because their main effect looks cosmetic. Forge's [1.20.x side documentation](https://docs.minecraftforge.net/en/1.20.x/concepts/sides/) distinguishes one-sided compatibility checks; its [1.20.1 handshake implementation](https://raw.githubusercontent.com/MinecraftForge/MinecraftForge/1.20.1/src/main/java/net/minecraftforge/network/HandshakeMessages.java) exchanges mod/channel/registry data. Required dependencies, channel version predicates and synchronized content still matter. A server's mod list is not a universal “every jar must be identical” rule, and a permissive display test alone does not prove channel compatibility.
- Keep all gameplay/content mods and their dependencies, and retain JEI/Jade/books for the planned observation layer. Do not replace the real handshake with the protocol bot's fabricated acknowledgements.

## 3. Server-side fake-player alternative

There are three distinct things that should not be conflated:

1. **[Fabric Carpet](https://github.com/gnembon/fabric-carpet)**, MIT, is a Fabric mod, not a native Forge solution. Its [1.20/1.20.1 release listing](https://api.modrinth.com/v2/project/carpet/version?game_versions=%5B%221.20.1%22%5D) identifies Carpet 1.4.112 dated 2023-06-08. A working Forge 1.20.1 port/Connector route was **not verified**; do not propose replacing the server loader.
2. **[Advanced Fake Player](https://api.modrinth.com/v2/project/advanced-fake-player)**, MIT, is a concrete **Forge/Fabric 1.20.1** option. [Forge 1.20.1 release 1.0.0](https://api.modrinth.com/v2/project/advanced-fake-player/version?game_versions=%5B%221.20.1%22%5D) is dated 2026-07-17; project metadata updated 2026-09-22. It advertises synthetic player spawning, possession and redirected GUI/movement inputs. **It requires installation on client AND server and a controlling real client**; it is not an autonomous, headless HTTP-controlled body. No public source URL or external agent API is provided in the fetched metadata; those are **UNVERIFIED**. Its broad mod compatibility claims are advertising, not this pack's validation.
3. **Forge's own `FakePlayer` is a utility, not a finished resident.** The [Forge 1.20.1 source](https://raw.githubusercontent.com/MinecraftForge/MinecraftForge/1.20.1/src/main/java/net/minecraftforge/common/util/FakePlayer.java), LGPL-2.1-only, extends `ServerPlayer` but deliberately makes `tick`, death, many packet handlers and network sends no-ops, and reports invulnerability. Simply spawning one does not create normal survival-player behavior. A custom **ticking `ServerPlayer` body**, lifecycle/connection facade and API/action scheduler would be a significant additional implementation.

**Architecture assessment (inference from the sources):** a custom server mod gains authoritative registries/world objects, recipes, inventories and server-side menu logic without an extra client JVM per bot. Forge's [1.20.1 menus documentation](https://docs.minecraftforge.net/en/1.20.1/gui/menus/) explains that menus reference underlying data and synchronize selected slots/data to clients; operating server-side can avoid that visibility boundary.

It loses the actual modded client: no client framebuffer, JEI GUI, client guide-book renderer or arbitrary client keybind/widget behavior. Custom client packets may need bespoke emulation. Mods that distinguish fake players, depend on a real connection or store per-player capabilities require testing. Exact behavior of this pack's security, teams, guns and machines with synthetic players is **UNVERIFIED**. Installing a new server mod requires a restart; mistakes run inside the valuable server JVM rather than an expendable client process. This is attractive for narrow automation but **not the preferred full-fidelity body**.

## 4. What the custom Forge 1.20.1 client API must expose

This is a proposed API design, not a claim that one existing mod already implements it all. “Any mod” must mean **the real client's supported interactions remain reachable**, not “every mod automatically has a structured automation API.”

| Surface | Implementation/API evidence and required contract |
|---|---|
| **Registry-driven observations** | Resolve block/item/entity/menu names from runtime registries, never a vanilla ID dump. Synapse's [1.20.1 state collector](https://raw.githubusercontent.com/Pendiv/Synapse/main/src/main/java/dev/div/synapse/core/StateCollector.java) already uses `ForgeRegistries.BLOCKS`, `ITEMS`, `ENTITY_TYPES`, `MENU_TYPES`. Add bounded nearby-block queries, blockstate properties, tags, collision/reach information, stack counts/durability and relevant NBT, plus dimension/tick. Distinguish **unknown/unloaded/not synchronized** from air/empty/zero. Do not promise hidden server block-entity data. |
| **Player actions** | Tick-scheduled movement/look, keybind press/release, attack/use-on-block/use-on-entity, hotbar selection and close-menu. Run on the game thread; route through real client interaction paths, not teleport/setblock commands. Supply a stop/release-all-inputs operation. Synapse's [endpoint contract](https://github.com/Pendiv/Synapse) is a starting point. |
| **Containers and inventory** | Read the real `AbstractContainerMenu`: menu/container ID, slot indices, full item identity/count, carried cursor stack, slot coordinates and permitted placement/pickup. ### The unavoidable non-generic GUI boundary

Synapse's [GUI implementation](https://raw.githubusercontent.com/Pendiv/Synapse/main/src/main/java/dev/div/synapse/core/GuiController.java), specifically Forge 1.20.1, enumerates `AbstractWidget` instances and handles `AbstractButton`, `EditBox` and container slots. That is a useful baseline, **not an accessibility tree for all mods**. Custom rendered buttons, tabs, tanks, energy bars, scrolling lists, drag gestures, radial menus and controls handled directly by a screen's mouse/key callbacks may not be slots or enumerated widgets. Their semantics and custom packet formats cannot be inferred generically.

Provide three layers: (1) structured slots and standard widgets; (2) screen-relative mouse/keyboard/scroll events with screenshots and observable postconditions; (3) explicit screen/mod adapters where reliable repeated operation requires them. A real client lets those events invoke the mod's own packet code, avoiding manual protocol reimplementation, but visual grounding can still fail. Machine state that is never sent to the client remains unavailable. These are the main reasons **“full-fidelity body” is achievable but “perfect generic structured use of ANY mod” is not a defensible guarantee**.

## 5. One staged recommendation for this server

### Architecture comparison

The following is a design assessment based on the cited APIs and supplied current-runtime behavior, not measured comparative performance.

| Architecture | Gains | Fidelity ceiling / costs | Fit |
|---|---|---|---|
| **Protocol bot + registry/recipe data dump** | Reuses current lightweight MCP process and working FML3 join; names/data can be enriched. | A dump cannot execute mod client code, custom screen logic or arbitrary mod packets. Each unsupported interaction still needs implementation. Actual additional RAM not measured. | Good for vanilla errands and research, **not this full-fidelity goal**. |
| **Real headless-display client + API mod** | Real Forge registries, content classes, packet handlers, mod menus, keybinds and rendered screens; can reuse Synapse/Baritone and existing MCP contracts. No new server mod required if bridge remains client-only. | Highest client-equivalent fidelity, but one substantial client JVM per bot; custom GUIs still need visual control or adapters. Estimated **6–9 GiB total RAM per bot**, UNVERIFIED. | **Recommended**: preserves the existing server and most directly meets the body requirement. |
| **Server-side ticking fake player + API** | Authoritative world/recipes/menu data; no extra rendered client JVM. | Server restart/mod installation; server-thread safety and mod-specific fake-player compatibility; no actual client GUIs/screenshots. Incremental RAM/CPU **UNVERIFIED**, not zero. | Potential later specialist worker, **not the primary resident body**. |

Pack-specific hardening and resident operation** | Exercise representative machinery, backpacks/accessories, claims/teams, dimensions and relevant keybinds; implement adapters only where generic input fails. Add per-instance identity/port/storage, lifecycle supervision, resource ceilings and small event streams; integrate existing resident schedule/memory behavior. | **3–6 days**, plus **1–3 days per genuinely unusual GUI/mechanic** | An hour-scale resident run survives reconnect/death/menu changes, respects claims, preserves item/account state and produces truthful action outcomes. Measure whether a second bot fits before enabling it. |

**Baseline total: 11–21 person-days** for a useful, integrated body/knowledge layer, **not** a promise to automate all 160 mods. Complete arbitrary-mod semantic coverage is open-ended; nonstandard mechanics remain the largest schedule risk. Reusing Synapse can reduce bridge boilerplate, but its multiplayer suitability remains an early gate ([documented singleplayer setup](https://github.com/Pendiv/Synapse)).

### What stays from the MCP runtime

From the supplied existing implementation, preserve tool names/contracts for `navigate`, `collect_block`, `craft_item`, `use_container`, `send_message`, status/world observations, `read_recent_events`, `note_save`/`note_read`, action IDs and `wait_for_action`. Keep resident persona, persistent files, schedules and model-provider selection outside the game JVM. These are **supplied local facts/design requirements**, not claims about a newly verified external release.

Reimplement execution, not the agent interface: navigation/mining → Baritone; chat → real client connection; container/crafting → actual menus and recipe facilities. Keep notes/events in the sidecar. Add low-level tools for inspect-menu/click-slot/widgets/input/screenshot/book/recipe lookup where existing high-level contracts cannot represent an unfamiliar machine; do not make `craft_item` claim arbitrary machine production has succeeded just because a recipe was found.

The in-client API should bind loopback, authenticate requests, separate observe/play from developer commands, schedule game work onto the right thread, serialize mutations, cap responses and return explicit unsupported operations. These are design requirements; Synapse's [security and access-level model](https://github.com/Pendiv/Synapse) already provides a useful starting pattern. Keep one resident per client; long actions progress locally between seconds-latency model turns.

### Main risks and decision

1. **Biggest risk: semantic GUI/mechanic coverage, not joining Forge.** A real client removes the protocol blind spot but custom screens/keybinds still require screenshots, deliberate input and sometimes adapters. Source basis: [Forge menus](https://docs.minecraftforge.net/en/1.20.1/gui/menus/) and [Synapse's actual widget coverage](https://raw.githubusercontent.com/Pendiv/Synapse/main/src/main/java/dev/div/synapse/core/GuiController.java).
2. **Host capacity:** 6–9 GiB/bot is an estimate; software rendering and startup peaks could make even that insufficient. Measure one on bazzite first; do not add resident clients to the memory-tight server laptop without measured headroom.
3. **Compatibility/version pinning:** HMC-Specifics lacks listed 1.20.1 support; HeadlessMC restricts offline accounts; Baritone's right release is 1.10.1, not 1.10.2; Fabric-via-Connector is not automatic. These pitfalls are documented above, not solved by this report.
4. **Safety and truthfulness:** pathfinding can modify the world, UI state can race, and client prediction is not a server acknowledgement. Require observed postconditions and bounded cancellation; preserve normal server protection checks rather than using privileged commands to bypass them.

**Choose the real-client + client-API architecture. First prove chat, a modded registry ID, a real machine slot transfer and a screenshot in one isolated instance.** That small milestone directly tests the full-fidelity premise before committing to broad automation.
