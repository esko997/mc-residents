# Resident full-client tools

Bun stdio MCP server for a real Forge client running Synapse and Baritone. No server-side bot or remote administration. Run this **on the client machine**, under the resident's account; keep Synapse loopback-only. Requires Bun 1.4+.

```sh
bun install
CLIENT_LOG="$HOME/gary-client/game/logs/latest.log" RESIDENT_NAME=Gary bun src/main.ts
bun test
bun run typecheck
```

Only MCP messages go to stdout; startup diagnostics go to stderr. Closing stdin, SIGINT and SIGTERM release held keys and send `#stop` (best effort if the client is unreachable).

## Environment

| Variable | Default / purpose |
| --- | --- |
| `CLIENT_LOG` | Required; client's `logs/latest.log`, followed across replacement/truncation. Existing lines are skipped at startup. |
| `RESIDENT_NAME` | Required; in-game name, used to ignore own chat echoes. |
| `SYNAPSE_URL` | `http://127.0.0.1:25599` |
| `SYNAPSE_TOKEN_FILE` | `~/.synapse/token`; token is never returned to the model. |
| `RESIDENT_DIR` | Current directory; `note_difficulty` appends `difficulties.md` here, and plans are kept in `plan.json`. Directory must exist. |
| `KNOWLEDGE_DB` | Optional read-only SQLite export; knowledge tools register only when it opens. Missing/invalid database is reported clearly on stderr; attempted knowledge calls return a tool error. |
| `COMMONS_URL` | Hub base URL, required for shared tools, e.g. `http://127.0.0.1:8770/`. No dashboard URL token. |
| `COMMONS_TOKEN_FILE` | Private file containing this resident's exact bearer token (no newline). Required with `COMMONS_URL`; identity and attribution come from the hub credential, not request arguments. |
| `RESIDENT_UNSEEN_PLAYERS` | `Lantern_`; comma-separated player names the body never perceives (see "Unseen players"). Empty for none. Case does not matter. |
| `RESIDENT_NAMES` | `Gary,Margo,Wren,Tobin`; every resident's in-game name. A chat line from anyone not listed (a person, the caretaker) always wakes `wait`; add a new resident here. |

Paths accept `~/`. Knowledge export/build instructions live alongside `scripts/build-knowledge.ts`; runtime lookup never contacts a service or generates recipes.

Shared stores are accessed only through the hub Resident API; the toolserver never opens the shared SQLite file or falls back to a local copy. Shared tools report a clear error when the hub is unreachable; body tools and private note/death recording still work. Private places remain in `RESIDENT_DIR/places.json`; shared places live in the hub table. A cancellable background long-poll feeds addressed events into `Events`; collaboration updates are non-waking. Mutations are never automatically retried.

Generate a token on each consumer with `../tools/new-commons-token.sh <file> <name> resident`; add the printed hash-only record to the hub's mode-600 credentials JSON array. See [Resident API deployment](../commons/README.md#resident-api-hub) for cutover order and endpoints. Install the sibling `commons` package as well: its pure contracts are shared by both packages, but no hub store executes in the toolserver.

For a Codex MCP client, use absolute paths (and the client's own home/token):

```toml
[mcp_servers.body]
command = "/home/your-user/.local/bin/bun"
args = ["/home/your-user/Repos/minecraft-residents/full-client/toolserver/src/main.ts"]
tool_timeout_sec = 180

[mcp_servers.body.env]
CLIENT_LOG = "/home/your-user/gary-client/game/logs/latest.log"
RESIDENT_NAME = "Gary"
RESIDENT_DIR = "/home/your-user/gary-client/resident"
KNOWLEDGE_DB = "/home/your-user/gary-client/knowledge.sqlite"
COMMONS_URL = "http://127.0.0.1:8770/"
COMMONS_TOKEN_FILE = "/home/your-user/gary-client/commons-tokens/Gary"
```

## Tools

- `wait` — Wait 1..120 seconds for chat, damage, death, a rescue/reflex, a player arriving or navigation; optional `for` event-type filter. Which chat lines end it: see "What chat wakes a wait".
- `alarm` — Shout a reason (1..120 characters) from your current body position. Manual limit: once per 10 seconds. Perceived alarms (heard within 48 blocks, or seen up to 96 with server-confirmed line of sight) wake `wait`; responding is the resident's decision, never an automatic movement.
- `go_to` — Start `#goto x [y] z`; `mode: "walk"` (default) forbids digging, placing and water-bucket falls for the whole trip. Explicit `"excavate"` permits them. Floats use the containing block (`floor`, including negative coordinates). Arrival means within two blocks, including height when supplied.
- `mine` — Start `#mine [count] namespace:block`, kept within `radius` blocks (default 32, max 96, three-dimensional) of where the call was made. Beyond that the body sends `#stop` and reports `navigation_stopped`; with `count` the body counts what came into the inventory and at that number sends `#stop` and reports `arrived`. See "Mine stays near", "Mine counts for itself" and "Blocks Baritone avoids breaking" below.
- `find_block` — The nearest blocks of a kind within `radius` (default 32, max 96; a sphere around the block the resident stands in), up to `limit` (default 8, max 16), nearest first, each with distance and compass direction. One `GET /blocks` to Synapse: nothing moves, loads or breaks, and Baritone is not involved. Any registered block can be found, natural ones included (ores, logs, crops); an id that names no block (`diamond`, an item) is an error. Only chunks the client has loaded are searched, and the reply says how many of the radius's chunks that was. See "Finding blocks" below.
- `follow` — Start `#follow player name`, with the same walk/excavate modes; following continues until explicitly stopped or replaced.
- `explore` — Start `#explore`, with the same walk/excavate modes.
- `stop` — Stop Baritone and release held keys; this is the explicit override even during a drowning or lava rescue.
- `status` — Position, dimension, health, food, held item, target, nearby players/hostiles, navigation and screen. With a plan written it adds two lines: the current step of the plan in focus (`Plan "wheat field": step 2 of 5: …`), blocked steps with their notes, `No step has moved for N min.` once that passes 20 minutes, then the goal and the other plans. Without a plan, one line saying `plan_set` exists, once per tool-server start.
- `inventory` — Non-empty inventory, armor and offhand, including durability; `H` marks hotbar indexes 0..8.
- `say` — Plain chat; rejects Baritone/slash commands and line breaks.
- `look` — Aim with yaw/pitch, block coordinates (floats use the containing block) or a nearby player name. A block look reports what is actually in the sights, including water and lava (the crosshair itself ignores fluids) and whether a fluid is a source block a bucket can take; it needs Synapse's `lookingAt.fluid`/`fluidSource` (`fluidsChecked`), and an older build says it cannot see fluids.
- `use` — Right-click, optionally hold for `hold_ticks` (1..200). With a bucket it reports what the bucket did: `Picked up minecraft:water from x,y,z`, `Poured minecraft:water at x,y,z against the up face of …`, or why nothing happened (no source block on the line, flowing water, nothing in reach). A boat, cart or player in the sights is refused before the click, since the click would board or interact instead.
- `attack` — Left-click and say what the click met (`Hit minecraft:zombie.`, `Struck … at x,y,z`, or nothing in reach). With `hold_ticks` the reply comes when the hold is over and says whether the block in the sights broke, with the tool's durability before and after, or that it is still there and why that happens (see "Held attacks"). A held attack hits a creature once only.
- `select_hotbar` — Select slot 0..8.
- `eat` — Eat food for 40 ticks; optionally name an item. Refuses open screens, moves off-hotbar food into a hotbar slot with a verified inventory swap, and fails if food does not increase.
- `open_inventory` — Open your own inventory, without replacing another screen.
- `screen` — Screen title, indexed non-empty slots, buttons and text fields.
- `click_slot` — Click a menu slot with optional button/mode; these are **screen** indexes, not inventory indexes.
- `craft` — Craft a shaped or shapeless recipe in one call (database required): at an open crafting table, or in the player's own 2x2 grid, which it opens when no screen is open. `count` is 1..16 crafting operations. One item per cell per operation, every click read back from `/gui`; the output is taken only when it shows the requested item, and on any failure the grid and cursor are emptied back into the inventory.
- `click_button` — Press a widget by label or index.
- `type_text` — Type into the current editor, including signs and books.
- `press_key` — Press ENTER, ESCAPE, BACKSPACE, TAB, arrows or DELETE; report the screen open afterwards.
- `close_screen` — Request closure, read back the screen, try ESCAPE if needed, then report whether it actually closed.
- `vehicle`, `mount`, `dismount` — Observe nearby vehicles and the current seat; board through ordinary entity interaction and leave through the vehicle's native controls, with observed confirmation. Airborne aircraft exits require explicit confirmation. No automatic action retries.
- `vehicle_control`, `vehicle_boost`, `vehicle_inventory` — Bounded native steering, aircraft boost, and the mounted inventory. `guide vehicles` covers vanilla boats/minecarts and the pinned Immersive Aircraft version. Foot reflexes do not steer, eat or sneak while mounted; plan fuel and landing.
- `storage_grid`, `storage_grid_take` — Search an already-open Refined Storage Grid and withdraw a specific displayed result, verifying the received count. Network results are not ordinary menu slots; server permissions still apply.
- `machine_sides`, `machine_sides_set` — Inspect and change the already-open Mekanism machine's native side configuration, checking each change. Requires a valid nearby menu and current access. Non-owner TRUSTED machines are refused because the client cannot verify trust-list changes and this mod version's server handler does not recheck them.
- `picture` — Return the actual framebuffer as MCP image content.
- `write_sign` — Put the selected sign against the looked-at face and enter up to four lines. It crouches first (a move window with sneak, released afterwards) so a chest, barrel, door or composter there takes the sign instead of opening or toggling, re-aims at the same face from the lowered eye and checks it, then reports `Placed the sign at x,y,z on the <face> face of <block>` or exactly why not: the sign stayed in hand (the space beside that face is taken or cannot hold a sign), a blank sign was placed without an editor, an existing sign, a vehicle seat, or a screen that opened instead.
- `write_book` — Write a book and quill from the inventory in one call and sign it (`title`, 1..15 characters) or keep it a draft (`draft: true`); `text` is laid out by Synapse with the editor's own rules, or `pages` are given. An empty book and quill is used; one with writing only with `replace: true`. Moves it to the hotbar when needed, writes, reads the slot back and restores the selected slot. See "Books".
- `read_book` — Whole pages of a written book or book and quill in hand, offhand, an inventory slot, or on the open lectern; continues with `page`.
- `book_register`, `book_find`, `book_report`, `book_update` — The hub's book catalogue: register a signed book (text read from the item, place from the sights), search with excerpts and distances, report it found elsewhere or missing, and (registrant only) change subjects/note or withdraw it.
- `records` — Dated records from the hub with their source: deaths, alarms, agreements (own and public), facilities, places, books, sessions, crossings, advancements, stats, building, flows, public chat, and the resident's own finished projects (`plan.json`). Windows as `6h`/`2d` or UTC dates; `around` narrows to an area.
- `find_item` — Search item names/ids (knowledge database required).
- `recipes` — Find item-producing recipes; shaped recipes include a grid legend (database required).
- `uses` — Find item-consuming recipes, including tags (database required).
- `guide` — Sourced practical and mod-progression reference plus indexed pack books. `query` accepts natural questions (for example "how to breed cows", "how to start Mekanism", "Refined Storage tech tree"); returned topic/section handles open bounded sections and continuations. Curated guides work without a database or network. Version labels and sources are visible; installed recipes and observed game behavior take precedence. Book search still uses the knowledge database when available.
- `mods` — The installed pack, as a player browses it with JEI and the advancement tabs (database required). No query: the kinds of mods (storage and carrying, tools/weapons/armour, guns, machines and power, redstone and security, magic, farming and food, building and decoration, exploration and travel, world generation, mobs and animals, quality of life) with their names; libraries, client-only and technical helpers are counted, and listed only for `query: "libraries"`. A kind: one line per mod. A mod (id or name): its description, what it adds, where its own advancement tab starts (first item there with a crafting or smelting recipe, that recipe, and the advancements it opens), a first craft (its item fewest crafting steps from things found in the world, with the step count and recipe), its book (with the `guide section:"books"` handle) and curated `guide` topic, a few items, dependencies and add-ons. `@mod words` lists the mod's items by name like JEI's `@` search. Replies page under 1,300 characters (`page`). Information only. `recipes` and `uses` start with the mod a modded item comes from; `what_next` ends, at the lowest priority, with the kinds of mods nothing carried or worn comes from. See "Pack overview" below.
- `note_difficulty` — Append dated text, position and last tool error for maintainers.
- `set_reflexes` — Configure `auto_eat`, `eat_below`, `when_attacked` (`auto`, `fight`, `flee`, `nothing`; see "Fighting back"), and the independently switchable `surface`, `escape_fire` (both fire and lava) and `avoid_creepers` rescues. Rescue switches default to `true`.
- `recall` — Keyword search of the resident's own notes (`memory.md`, `journal.md`, `notebook.md`, `notes/**`); never `archive/`. `limit` at most 8.
- `place_save`, `place_find`, `place_remove` — Named coordinates kept as data: private in `RESIDENT_DIR/places.json`, shared through the hub's `shared_places` table. `place_find` lists nearest first (at most 10) and includes the last five deaths with their age.
  Optional refuge metadata records access, hazards and when the resident checked the place. These are dated reports, not a safety guarantee or an automatic teleport/escape route.
- `skill_save` — Save or revise the resident's own skill: JavaScript (the body of an async function) plus an optional `expect` check (`gain`, `lose`, `near`, `screen`). Syntax errors are reported with their line. Changing code or check bumps the version and makes it a draft again.
- `skill_find` — Keyword search over the resident's own skills and everyone's verified or curated ones; each line shows status, author, args and three separate figures: runs that passed the check, other residents who used it, and their feedback.
- `skill_show` — One skill in full: description, args, check, record, review, feedback, latest runs and code (`from_line` continues long code).
- `skill_run` — Run a skill with `args`; `max_seconds` 1..600 (default 120). Reports finished/stopped and why, the check with observed numbers, inventory changes, what the code returned, and the last log lines.
- `note_share` — Propose a piece of knowledge (up to 600 characters) to the other residents; they see it only once a reviewer has curated it.
- `notes_shared` — Search curated shared notes, plus the resident's own proposals with their status.
- `feedback` — Say whether another resident's skill or a curated note worked (`worked` true/false, optional `text`); one verdict per resident per target, replaced by a later one.
- `plan_set` — Write or replace a medium-term project (`src/plan.ts`, `RESIDENT_DIR/plan.json`, atomic writes): `name`, outcome `goal`, vision link `why`, observable `done_when`, optional `needs`/collaborator `with`, and 1..12 immediate `steps` (usually 3..7). Up to three open projects, one focus; unchanged steps retain state. Legacy files load intact and ask for missing criteria. Text/note edits do not reset the action-progress clock.
- `plan_step` — Set a numbered action (`step`, or `all: true` for still-open actions) to `todo`, `doing`, `done`, `blocked` or `dropped`, with an optional concise `note`. Checked actions do not close the project: it remains awaiting outcome verification.
- `plan_finish` — Explicitly close a project. `outcome: "done"` requires closed actions, a completion criterion and nonempty `evidence` describing the observed result; optional `unlocks` records a capability made available. This is resident-reported evidence, not automatic world verification. `outcome: "dropped"` records abandonment separately. History retains ten endings; legacy endings remain labelled unverified.
- `plan_show` — Open projects plus recent endings, or full project details by `name`. Long results give a `page` continuation rather than losing steps or evidence to truncation.
- `plan_focus` — Choose the project whose next action or pending verification `status` shows. Survives restarts and context summaries.
- `what_next` — At most five suggestions computed from one snapshot (inventory, armour, health, food, saved places, deaths of the last six hours, the plan in focus), most useful first, each with the numbers it rests on; no model call. The current step of the plan in focus is the first line. The rules are the `rules` table in `src/ideas.ts`: a rule is `{ id, priority, suggest(view) }` returning text or nothing. Recipes are checked against the knowledge database when it is open (tags included); otherwise against the vanilla recipe written in the rule. Reply capped at 1,300 characters.

Not registered: `src/wiki.ts` is a newer-version vanilla wiki prototype, not the active reference interface. `guide` supplies version-scoped starter references and body-control translations instead; it is not an unrestricted web browser or an exhaustive encyclopedia.

**Progression and shared learning.** Persona visions establish Gary's settlement-building and Margo's Mekanism/Refined Storage/Immersive Engineering purpose. Reliable *access* to essentials counts, so specialisation need not duplicate farms. Projects connect those visions to short action plans and completion evidence. `skill_find`/`skill_save`/`skill_run`, shared notes and feedback remain the reusable learning layer; no second skill store was added. Useful outcomes should unlock the next project, not reward more plans or notes. The caretaker digest includes project criteria, reported evidence, neighbour projects, shared places and available verified/curated skills. It may point out a dependency, unused means or relevant guide query without imposing a full plan.

`status` also lists up to six nearby cows, sheep, pigs and chickens with IDs,
current coordinates and distances, nearest first. This supports the husbandry
reference without inventing an entity-targeting tool; `look` coordinates still
aim at a block centre, and `picture`/yaw/pitch may be needed to feed a moving
animal. Adult/baby status is not inferred from position.


Events that carry what the resident needs to decide for itself: `died` gives the block and dimension and that dropped items last about five minutes; `navigation_stopped` says a trip was ended by its body (goal, reason, where it stands, distance left, and a count when it recurs within ten minutes): always after a lava rescue, after drowning rescues only when breaths were not getting it closer or the head could not be kept above water, and with `reason=you died` when death ends a trip (Baritone is stopped; no trip starts before respawn); `stopped_short` adds `attempts=N` from the third consecutive failure of the same goal from about the same place, and for a goal with a height `across=` and `height=goal is N above|below you`, since most stops with a height are on the spot but not at that height. A stop is four seconds with no step, no turn of the view, no change of the block in the sights and no Baritone reply, or 30 seconds without a step: breaking blocks from one spot is not a stop. `follow` reports `arrived` within four blocks, because Baritone keeps three from the player. Baritone's `Paused`/`Resumed`, answers to the body's own reflexes, never replace the last reply shown in `baritone=`.

**Trip boundaries.** A mode change first stops the old Baritone process, reads and saves its settings, then applies and checks the new settings before starting. Walk mode refuses a nonempty `allowBreakAnyway` exception list rather than claiming it cannot dig. Settings are restored when a job is confirmed finished, stopped, replaced, abandoned, or the body shuts down. Arrival alone does not prove Baritone has released control: the body checks `#proc`. `mine` is explicitly excavating and retains its local radius/count controls. Constructed-block costs remain a heuristic only in excavating mode; no provenance detector is implied.

**Mine stays near.** Baritone 1.10.1 has no radius for `#mine`: it walks to the nearest block it knows in the loaded chunks however far that is, and with `exploreForBlocks` (default on) wanders at random when it knows none. The body therefore keeps the job near in two ways. On every poll it measures the body's distance from where the call was made. And from 0.5 s after the start, every 3 s, it sends `#proc` and reads the answer from the log (the five lines never become events and are no sign of life for the stall clock): `Display name: Mine …` naming the block, then `Last command: … GoalComposite[GoalTwoBlocks{x=,y=,z=}, …]` listing every block Baritone is heading for, or a `GoalRunAway…` when it knows none and explores. When the body is past the radius, the nearest listed block is past it, or Baritone explores, the body sends `#stop` and adds one event: `navigation_stopped goal=mine 1 supplementaries:wild_flax collected=nothing reason=no supplementaries:wild_flax left within 32 blocks of where you started (0,64,0) nearest=150,64,0, 150 blocks from where you started you=0,64,0`. `collected` is what the inventory gained since the start (`3 x minecraft:oak_log, 1 x minecraft:stick`, at most three kinds, counted items first), `counted=3 of 8` follows it when the job had a `count` and something came in, and `nearest` is present when Baritone named a block (`none known in the loaded chunks` when it explores). Only what Baritone said is claimed: the reason is `the way to the next <block> led more than <radius> blocks from where you started (x,y,z)` when a block inside the radius is known but the path left it, and `you were more than <radius> blocks from where you started (x,y,z) before Baritone said where it was heading; whether any <block> is left near there is not known` when the body was past the radius before any `#proc` answer had been read. The radius still holds after a `stopped_short` for the job, because a hard block outlasts the four-second stall clock and Baritone walks on afterwards; it ends when `#proc` has answered `No process in control` twice running (the first such answer can come before the job's first tick, so it is only asked again 0.5 s later). A job paused by a reflex is not asked about until the pause ends.

**Mine counts for itself.** Baritone's own count can remain zero after collecting the target. The body instead measures net inventory gains once per second, in the target's own item and what it drops: known vanilla drops first; else the block's loot table from the knowledge export (`block_drops`, built from every jar's `data/*/loot_tables/blocks/*.json`, ordinary-tool entries only; rebuild the export to get it); else, for a modded `_ore`, the vanilla ore its name ends in (`denseores:dense_iron_ore` counts `minecraft:raw_iron`, as `minecraft:iron_ore` would). Unrelated pickups do not count. The `mine` reply names the counted items and how the drop was known; when none is known only the block's own item counts and the reply says the count may not finish, so use the reported inventory and `stop`. Count completion sends `#stop` and reports `arrived`; radius exits report what was collected and counted. Same-item ground pickups count, and blocks placed from that stack reduce the net gain; this is not a count of broken world blocks.

**Blocks Baritone avoids breaking.** The generated `<game dir>/baritone/settings.txt` sets `blocksToAvoidBreaking` and `avoidBreakingMultiplier 0.01`: constructed-looking blocks cost more to break, but are not forbidden. Natural logs and cobblestone remain ambiguous; this is not placement tracking. Explicit mining of a listed block temporarily lifts the multiplier to 1, then restores the previous value on count, radius, stop, death, abandoning rescue, another trip, shutdown, or two no-process replies. A stall report alone does not end an active job. Failed setting calls are retried on the next poll. **The lift is global:** other listed blocks on that mining route also become cheaper to break. The next tool-server start restores a stale multiplier of 1 to 0.01, but cannot reconstruct the interrupted mine watch. Keep explicit mining away from buildings; after an interrupted tool server, stop any leftover navigation. The launcher reinstalls the generated defaults at client start.

**Finding blocks.** `find_block` asks Synapse's `GET /blocks?block=<id>&radius=<1..96>&limit=<1..32>` (defaults 32 and 8; the tool sends at most 16) and so needs a Synapse build that has it; an older one answers `Unknown endpoint`. The mod reads the block states of the chunks the client holds for the current dimension, as they are at that moment: no Baritone cache, so there is no list of "recorded" blocks and nothing remembered from places since left. It answers `{ block, dimension, origin: [x,y,z], radius, limit, positions: [[x,y,z], …], truncated, chunksLoaded, chunksInRadius }`. `origin` is the block the player stands in (`floor`, also below zero); a block counts when `dx² + dy² + dz² <= radius²` between block coordinates, so one exactly `radius` away is in and height counts like any other axis. `positions` are nearest first, ties by x, then y, then z; `truncated` says more matches lie in the radius than were returned (`there are more` in the reply). `chunksInRadius` counts the chunk columns the radius touches and `chunksLoaded` those the client holds; the rest were not read, which gives three different empty replies: `No X within N blocks of you (x,y,z); every chunk in that radius was searched (18).`, `No X in the loaded chunks within N blocks of you (x,y,z), but only 17 of the 18 chunks in that radius are loaded in your client; the rest was not searched.` and `Nothing was searched: no chunk within N blocks …`. With matches the same count stands in the first line, before the list, because a long reply is cut from its end. What it does not do: load or request chunks, look past 96 blocks or into another dimension, or check that a block can be reached (the last line of a reply says so; `go_to` or `mine` finds out). The mod refuses an id that is not a registered block, and air; a malformed id, radius or limit is refused by the tool's own schema before any request. Cost in the client is bounded: air-only sections and sections whose palette lacks the block are skipped, sections are read nearest first and reading stops once nothing unread can be nearer than the matches kept, and one main-thread task reads at most 64 sections.

Bare ids for `mine`, `find_block`, `eat`, `recipes` and `uses` assume `minecraft:`. When an exact recipe/use lookup is empty, matching indexed item ids are tried and any selected alternate id is reported.

**Pack overview.** `scripts/build-knowledge.ts` also writes what `mods` reads, all from the jars (`src/knowledge/pack.ts`): `mods` (one row per `[[mods]]` entry of `mods.toml`, inline `mods = [{…}]` included, or `fabric.mod.json`; jars nested under `META-INF/jarjar` are read too), `namespaces` (which mod owns each asset/data namespace), `registered` (an item with an English name and an item model or blockstate; blocks marked; TaCZ gun-pack guns, ammo and attachments from `assets/tacz/custom/*/data/*/index` inside the jar, with their gun-smith recipes; gun packs added to the game's own `tacz/` folder are not read), `advancements` (displayed, not hidden) and `books` (Patchouli, Modonomicon, the IE manual). Per mod it stores counts, its own recipe types and the blocks named like them, its advancement tabs, the tab's first craftable item (a recipe that only turns the item's own nuggets back into it does not count), a first craft and a few signature items. The first craft ranks the mod's items made in a crafting grid or furnace (mods' own grid types included) by steps from the world across every mod: vanilla items, blocks no recipe makes and what natural blocks drop (raw ores) are 0; other unmade items (loot, mob drops) 3; each recipe is one step more than its dearest input, and a machine recipe also needs its machine (the block named like its type, else 2). So an add-on's part built from its parent's alloys counts as deep, not as "nothing from the mod". Ties go to the mod's namesake (a Backpack in Sophisticated Backpacks), then to the most used item (direct uses, uses of a tag of three or fewer items, and recipes made in it). Recipe `mod_loaded` conditions now use only declared mod ids, so a mod named as an optional dependency no longer counts as installed. Sorting mods into kinds is the one judgement made at runtime (`placeMod` in `src/mods.ts`: keyword scores over each mod's name, description, item words and recipe types, plus a short corrections table); a mod added later is sorted from its own data. An export built before this answers `mods` with a request to rebuild; `recipes`/`uses`/`what_next` simply omit the mod lines.

**Limits.** A `limit` above a tool's cap (`find_block` 16, `place_find` 10, `recall` 8, `skill_find` 10, `notes_shared` 8; read from each schema) is lowered to the cap rather than refused, and the reply begins `Asked for 20; showing at most 10, the most place_find lists.`; the tool's own `N more not shown` line still follows. Any other invalid argument, including a limit below 1 or a radius over 96, is still an error.

**Unknown arguments.** `wait`, `use`, `attack`, `eat` and `click_slot` now refuse a key they do not take, like `look`, `mine`, `craft`, `mount` and the shared tools already did: `until is not an argument of wait, which takes seconds, for; for until, use for to list the events that may end the wait.` The call logs of 2026-11-22/23 show these five silently ignoring keys on calls that then ran: `wait` `until` 203 times (Margo 201), `use` `hand` 5 and `x`/`y`/`z` once, `eat` `slot` 4, `click_slot` `action: "QUICK_MOVE"` 3 (each one became a plain pickup), `attack` `ticks` once. `find_item` stays lenient: its 9 ignored `limit`s cost nothing (it always lists up to 12). Tools whose unknown key came with a missing required one (`say` `message`, `note_difficulty` `detail`) already fail on the missing key.

**Unseen players.** The owner watches through a spectator account, and a person cannot see a spectator, so the body never perceives the players in `RESIDENT_UNSEEN_PLAYERS`. Every state read (`Synapse.state`, used by `status`, `look`, skills' `state()`, `what_next`, the reflexes and `player_near`) leaves them out of the nearby entities, and the crosshair resting on one reads as nothing in the sights; `attack` then sends no click. `look {player}` and `follow` answer `Player Lantern_ is not nearby.` Their chat, and every system or Baritone line naming them (joining, leaving, advancements, deaths, whispers), is dropped as the log is read: no event, no event number, no wake, no dropped count. Synapse does not report other players' game modes (its `gameMode` is the local player's), so a spectator not on the list is still seen; see the Synapse notes below. A picture of the screen is not filtered, but a spectator is invisible to a survival client anyway.

**What chat wakes a wait.** A chat line ends a `wait` (one that allows `chat`) only if it names this resident as a whole word in any case; or its speaker is not in `RESIDENT_NAMES` (a person, or the caretaker, who now speaks to one resident with `tellraw <Name>`); or the speaker was within 48 blocks when the body last sensed them (the players in its latest full state, which Synapse reports out to its `stateRadius`, 16 blocks by default; no hub question is asked); or an exchange is under way: this resident's own `say` named the speaker, or the speaker named this resident, in the last 120 seconds. Every other line is still in the next tool result's event tail, exactly as before; it only does not end the wait. The rule lives in `src/hearing.ts`.

## Skills

A skill is a routine a resident wrote once and can run again in one call; the Commons hub keeps it, so it survives sessions and the other residents can use it. Statuses: `draft` (author only) → `verified` (a run by its author finished and passed its `expect` check; visible to everyone, not yet reviewed) → `curated` or `rejected` (set by a reviewer through the management app). A skill without `expect` can never be verified. Three records stay separate everywhere they are shown: whether runs passed the check (`skill_runs`), how many residents other than the author ran it, and those residents' `feedback`.

**What skill code is.** It runs in QuickJS compiled to WebAssembly (`quickjs-emscripten-core` with `@jitl/quickjs-singlefile-cjs-release-sync`: pure WebAssembly embedded in the package, no native build, installed by `bun install`), a separate JavaScript interpreter inside a worker thread (`src/skill-worker.ts`, driven by `src/sandbox.ts`). Its global object has the language built-ins and nothing else: no `Bun`, `process`, `require`, `import()`, `fetch`, timers, files, network, environment, commons database or tool-server objects. All it can do is:

- `await body.<tool>(args)` — any body tool the resident has, returning the tool's text without the event tail. Closed to skill code: `skill_save`, `note_share`, `feedback` (the resident's own word) and `picture` (an image). A tool error is thrown as an error with `.tool` and `.message`; uncaught, it stops the run. `say` is limited to five messages per run.
- `await state()` — `{pos, dimension, health, food, air, screen, lookingAt, held, selectedSlot, hotbar, inventory, nearby, onGround, inWater, inLava, onFire, navigation}`; `inventory` maps item id to total count (inventory, armour and offhand), `nearby` is the 24 nearest entities with `type`, `name`, `distance`, `hostile`, `player`, `x`, `y`, `z`. Read at most five times a second when nothing else is called in between.
- `args`, `log(text)` (the last lines appear in the report), `await sleep(ms)`.
- `await body.skill_run({name, args})` — other skills, two levels deep, inside the same time and tool-call budget. A called skill that stops or fails its check throws.

Limits are enforced outside the interpreter: wall time (default 120 s, `max_seconds` up to 600), 300 tool calls per top-level run, 64 MB of memory, 400 KiB of stack. An endless loop is ended by the interpreter's interrupt handler and, failing that, by terminating the worker; the tool server's own thread, and with it the poller and the rescues, never waits on skill code. If the interpreter cannot be started, `skill_save` and `skill_run` refuse with one line; skill code is never run in the tool server's own JavaScript engine.

**A run and the body.** `skill_run` is not itself a manual action. Each tool the code calls takes the same path as a call from the resident, so `takeoverTools` still interrupt a fight or a meal for just that call and reflexes act between calls. The run stops at once, saying why, when the resident dies, when a rescue, flee or fight reflex starts (so the code's next action cannot take the body away from the rescue), when a tool error is not caught, at a limit, or when the MCP call is cancelled. It will not start while the resident is dead or a rescue is under way. `wait` inside a skill counts only events since the run's previous `wait` and returns those event lines after its first line, so `go_to` then `wait` works any number of times in one run; the resident still gets all events in the tail of the `skill_run` result. After the run the check is evaluated from state read before and after, the run is recorded in `skill_runs` (`ok`, `check_ok`, `error`), and a draft whose run finished and passed becomes `verified`.

Codex and Claude give an MCP call 180 seconds here (`tool_timeout_sec`, `MCP_TOOL_TIMEOUT`); a `max_seconds` above about 170 needs those raised, otherwise the client cancels the call and the run stops as cancelled.

## Body behavior

One shared poller reads summary at 4 Hz and full state at 1 Hz (also on damage, and at every poll while a hostile is within 8 blocks or a fight is on). Waits subscribe to its events, never add HTTP polling. Chat comes from a 50 ms local log tail, including phone-style system chat. Every tool result ends with unseen events, at most eight and at most 1,000 characters, with an older-dropped count: when they do not fit, the oldest are left out whole. A chat or system line is never cut (limit 320, a full 256-character line with its sender; three such lines fit); other lines are cut at 91 to 380 characters by type (`navigation_stopped` 380, `reflex` 300) and then end in `…`. Text is capped below 1500 characters with explicit omission; screenshot image bytes are separate. Large inventories/menus/recipe lists can therefore be abbreviated.

Reflex defaults: auto-eat below 12 food, and also below 14 health when food is below 20 so regeneration can start; `auto` attack response fights back only with a sword/axe in the hotbar and at least 8 health, otherwise flees (the event states why). Both automatic and explicitly configured fights break off and flee at 6 health or below. Food detection uses Synapse's edible metadata (including modded foods), with a vanilla-food fallback only for older payloads without that metadata. Each automatic meal produces one completion event with item, any inventory move, and observed food before/after (or a failure). Screens suppress reflexes; a screen blocking meals for more than 20 seconds at low food produces one warning until unblocked. Only hands/view/hotbar tools (`look`, `use`, `attack`, `select_hotbar`, `eat`, `open_inventory`, `close_screen`, `click_*`, `type_text`, `press_key`, `write_sign`, `stop`) take over automatic behavior; navigation, chat, waits and observations leave it running. A navigation command issued during a fight or a rescue is kept paused until that reflex ends.

**Fighting back** (`src/fight.ts`, `Body.fightBack`/`fightOn`). A model turn takes 5 s or more and a zombie hits every second, so the body defends itself at its own polling rate, without a model turn:

- *When.* The body was just hurt with a hostile mob within 6 blocks (Synapse cannot say who hurt it, so the nearest hostile is taken), or a hostile mob is within reach (3.5 blocks centre to centre) and closer than at the previous full read. Coming close is no attack from a neutral mob (enderman, zombified piglin, piglin), so only being hurt starts a fight with one. It never targets or aims at a player, a passive animal or a creeper (but see the race below); never hunting.
- *How.* It pauses a running trip, selects the hotbar's best sword or axe by vanilla damage per second (a modded one of unknown material counts as iron), and swings at the chosen mob only once the weapon's attack cooldown is over (a sword 0.68 s, axes 1.0 to 1.3 s, a hand 0.3 s; changing the held item restarts it). Each swing aims at the middle of the mob, reads the crosshair two client ticks later, and sends the click only when that mob, and nothing else, is in it.
- *What it can guarantee.* The crosshair read and the click are two separate client-thread tasks, a few milliseconds apart (one HTTP round trip), and Synapse clicks whatever is in the crosshair when the click task runs. So the click carries the mob's id (`expectEntityId`): a Synapse that knows it checks the crosshair in the click's own task and refuses (`struck: false`) when anything else is there, and the refused click is not counted. The Synapse deployed so far (2026-11-23) ignores the field, so with it a player or animal stepping into the line inside that gap would take the swing. The check is in Synapse's `PlayerController.attack` on `dedicated-server`; built and checked live on gary_fc_test on 2026-11-23 (a wrong id was refused and left a pig at 10 health, the right id struck it to 9), not yet deployed to the residents.
- *Mobs that shoot* (skeleton, stray, pillager, witch): the body closes in with five-tick sprint steps, only on dry ground, not toward a drop, at most 6 blocks from where the fight began, and stops after 1.5 s without getting half a block closer. Flying or other ranged mobs out of reach are not chased. Either way the end line says the mob stayed N blocks off, and for a shooter that getting out of its line of sight is safer. A hissing or close creeper is the `avoid_creepers` retreat's, which interrupts a fight.
- *Ends* when no hostile was within a clear swing (or hurt the body) for 2 s, at 20 s, at 6 health (it hands over to the retreat), on a higher rescue, a screen, death (silently: the `died` event says it) or a hands tool. Keys are let go, the previous hotbar slot is restored and a trip it paused is resumed. A mob it gave up on (out of reach, never a clear swing, the 20 s cap, or the resident took over) starts no new fight by coming close for 30 s, only by hurting the body from within reach.
- *Reports*: one line when it starts, `fighting back against minecraft:zombie 2 blocks away (you were just hurt) with minecraft:iron_sword in H2, health 18; walk paused`, and one when it ends, `fight ended after 3.4 s: no hostile within reach for 2 s; minecraft:zombie killed (2 hits, health 20 -> 9); 2 swings; your health 18 -> 18; walk resumed`. A mob is `killed` when its health reads 0 or it vanished within 2 s of a hit; a hit is a swing Synapse reports landing on an entity.

**Held attacks.** Vanilla keeps breaking a block under a held attack only while `Minecraft.handleKeybinds` passes `MouseHandler.isMouseGrabbed()` to `continueAttack` (checked in the 1.20.1 bytecode), and a window grabs the mouse only when it has input focus as the world loads or a screen closes. Resident clients run on a shared X11 desktop (`launch.sh`, `DISPLAY=:0`, `pauseOnLostFocus false`), so with a Synapse built before the fix a hold in any other window gives one click and no more. On 2026-11-23, 01:03 to 02:40 UTC, Gary's holds on chalk, bauxite, amethyst and obsidian changed nothing (six `note_difficulty` reports) while Margo's 194-tick hold broke the same obsidian with the same pick. Synapse with the fix (`dedicated-server`, "Held attacks" in its README) opens that gate for its own hold while the crosshair stays on the hold's target, numbers the hold in its reply (`id`) and reports it in the state as `attackHold`. With it, `attack` waits until the hold is over (sooner when the block breaks) and, when the block is still there, says how far breaking got, about how many ticks the block needs with the held tool, and why the hold ended (all ticks held, the crosshair left the block, a screen, a release, death). With an older build the reply says that build needs window focus and waits out the whole hold. Baritone's `mine` breaks blocks through the controller and is unaffected either way. Checked live on gary_fc_test on 2026-11-23 with X input focus on another window: the old build left stone standing after a 60-tick wooden-pickaxe hold; the fix broke it in 23 ticks and stopped at the glass behind it, and a 60-tick bare-hand hold reported 37% of an about 150-tick break.

Survival rescue priority is lava, drowning, fire, creeper, being attacked, then eating. A higher-priority rescue interrupts a meal, fight or lower rescue; start and end emit one `reflex` event each and wake a pending `wait`. Drowning and lava rescues retain the controls against ordinary manual actions; `stop` is the explicit override. Cleanup releases held keys and handles navigation according to the rescue outcome. Fire view/hotbar state is restored before resumption. Missing fields never default to false/zero: the affected rescue stays off and `status` reports the older-Synapse warning. While mounted, foot rescues and automatic meals are suspended so they cannot eject a passenger or interfere with flight.

**Alarms.** Damage with a hostile within six blocks, health below 30% (6/20), a close creeper, and lava raise fire-and-forget alarms through the hub. Each automatic reason class is locally and centrally limited to once per 30 seconds. An unavailable hub cannot delay a rescue. Receivers take a fresh body position (`alarmPerception` in `src/alarms.ts`, three-dimensional distance, same dimension only): within 48 blocks an alarm is heard (`alarm Margo 34 blocks north-east: …`); from 48 to 96 blocks the body asks the hub `GET /resident-api/v1/sight?to=<sender>` (its own sight only; 2.5 s client bound, fire-and-continue so neither the events poller nor a reflex waits) and the alarm is perceived only when the server observer confirms a clear line of sight (`alarm Margo 80 blocks east, in sight: …`). Blocked, unknown (no observer, other dimension, unloaded ray), slow or failed answers, other dimensions and anything farther produce no event or mind-visible log. Lines give sender, rounded distance, eight-point direction, reason and optional health. The global public-chat relay is suppressed from resident log events so it cannot bypass earshot; humans still see it in game and on the dashboard.

- **Safe-ground trail and retreat:** The poller retains 40 observed grounded, dry, cool positions. Retreat prefers a crumb leading away from the threat; otherwise it tries bounded headings away and to either side, remembering directions that produced no movement. It seeks ten blocks of separation, runs for five seconds, and extends only while separation improves, never beyond eight seconds. Falls, unsafe footing, blocked routes and timeouts are reported rather than called successful escapes. This is reactive steering, not a guaranteed path to a saved refuge.
- **Drowning (`surface`):** If `underwater` is true and `air < maxAir / 2`, pause Baritone and hold jump in repeated five-tick steps. During a trip this is a breath: once air is back to 80% the same trip is resumed. The trip is stopped, with the numbers, on the third breath within two minutes that brought it less than 8 blocks closer (or the third at all for goals without a destination), or when 12 seconds pass without air recovering. With no trip under way the body surfaces and then makes for the latest safe crumb. The end event reports observed air before/after.
- **Lava and fire (`escape_fire`):** In lava, pause and use repeated jump+sprint steps toward the latest safe crumb until observed out (10-second timeout). Burning outside water/lava uses a hotbar water bucket when outside the Nether: select it, look straight down, place, retrieve after one second, restore slot/view and resume. Without a usable bucket the fire is only reported, without pausing navigation.
- **Creepers (`avoid_creepers`):** A creeper with `fuse: true`, or any creeper within three blocks, starts retreat before damage. Combat never attacks a creeper, including when `when_attacked` is `fight`.

`status` adds air while underwater and a burning/lava hazard line. These rescues require Synapse's `air`/`maxAir`, fluid/contact, burning, grounding and creeper-fuse fields; the older-payload fallback applies only when those senses are unavailable.

Meals use the hotbar first, otherwise open the survival inventory and swap the food stack to an empty hotbar slot (or the selected slot if full, reporting the displaced stack). They verify the hotbar and close the inventory before using food. To avoid right-clicking the crafting table/chest in front of the player instead of eating, meals aim straight up, wait two client ticks for the raycast, and restore the selected slot and aim after releasing use. Synapse's sneak movement can coexist with held use, but its acknowledgement arrives only after movement ends; it cannot guarantee sneak-before-use ordering. If a screen nevertheless appears during a meal, use is released before verified closure, one reflex event reports the failed meal, and auto-eat waits 10 seconds before trying again. This also prevents close/reopen loops. The mod's close acknowledgement now reflects the actual screen instead of unconditional success; real modpack behavior still requires live verification.

A held use lands on whatever the crosshair rests on when the hold begins, and Baritone turns the view on every tick it works. So a meal pauses Baritone while a trip is known (resumed on release, and not counted as a stall), and after looking up it reads the state back: if the view did not stay up, or an entity or a block that opens (table, chest, door, trapdoor, sign and the like, by name) is overhead, nothing is used and `Meal not started: <reason> Auto-eat retries in 10 s.` is the one event (`eat` returns the reason as its error). Death during a meal lets go of the keys and nothing else: the death screen is not treated as a screen the meal opened, nothing is clicked or closed, and the `died` event is the only word on it.

An open screen blocks meals, and live a forgotten furnace screen did so at food 5 for four minutes. So at food 6 or less, when a screen other than the death screen has been open for 30 s without a screen action by the resident (`use`, `open_inventory`, `screen`, `click_slot`, `click_button`, `craft`, `type_text`, `press_key`, `close_screen`, `write_sign`, from the resident or from skill code) and food is carried, the body reads `/gui`; with nothing on the cursor it closes the screen and eats, and the meal's one reflex event names both: `closed FurnaceScreen (no action for 30 s) to eat; ate minecraft:bread, food 5 -> 11.` (or `…to eat; Meal not started: <reason> Auto-eat retries in 10 s.`, `…to eat; the meal was cut short`, `…to eat; the meal has not started` when a rescue or a fight came first). A stack on the cursor, an action in the last 30 s, food above 6 or no food carried leave the screen alone and the 20-second warning as before; the cursor is looked at once a second, and a screen that will not close is tried again after 30 s.

Requires Synapse's timed use/attack, `release`, sprint movement, GUI character/key input, `eye` position, and player names/hostile flags in full state. Unknown modded enemies require Synapse's hostile flag; no registry-name guessing. Minecraft server corrections, claims, food consumption and sign persistence remain authoritative. A path reports `stopped_short` after four seconds without movement **or a fresh Baritone reply**, including the last reply since that navigation started and the distance left. Mine/explore have no fixed destination, so their remaining distance is explicitly unknown. The timer is an inactivity heuristic, not direct access to Baritone's calculation state. Mining command syntax was checked against [Baritone 1.10.1 MineCommand](https://github.com/cabaletta/baritone/blob/v1.10.1/src/main/java/baritone/command/defaults/MineCommand.java).

## Books

`write_book`, `read_book` and the catalogue tools use Synapse's `/book` endpoint (`dedicated-server` branch, not yet deployed; an older Synapse answers that it has no `/book`, and the tools say so). Synapse does what the book-and-quill editor (`BookEditScreen`, 1.20.1) does, checked against the mapped bytecode: a page is kept while it is under 1024 characters and `font.wordWrapHeight(page, 114) <= 128` (14 lines of the client's own font), a book has at most 100 pages, a title is 1..15 characters after trimming, and no `§`, control character or DEL is accepted (pages keep line breaks). The server bounds the packet only (200 pages of 8192, a 128-character title) and keeps the first 100 pages, so these are the real limits. Signing sends the editor's own `ServerboundEditBookPacket` for the selected slot (or 40, the offhand) with no screen open; the tool then reads the slot back and reports what the server made of it. Driving the editor through `type_text` was not used: the editor drops characters that overflow a page without saying so, and Synapse's `/gui` cannot read a page back.

Reading: Synapse reads the item in the player's own inventory (or the lectern menu's book while its screen is open) and returns pages as the book screen shows them (`Component.getString()`, literal fallback). A chiseled bookshelf is not readable in place; `use` on an occupied slot moves the book into the inventory.

The catalogue stores what the registrant's body read from the item, never text the model supplies. Each copy is its own entry; `text_key` (title, author, pages) groups copies of any generation, and `content_hash` is the server bridge's `resident-book-v1` hash, so a registered library shelf read (`/v1/library/shelf`) marks a copy seen or not seen there. Moves and missing books are dated reports. Hub side: `../commons/src/library.ts`, `records.ts`.

## Synapse additions

The toolserver works with today's build. Written but not yet deployed: `expectEntityId` on a single `attack` (see "What it can guarantee" above) and the held attack that keeps breaking without window focus (see "Held attacks"). These would make the rest exact (none is implemented; all are client-side reads in the mod):

- **Other players' game mode.** `nearbyEntities` names players but says nothing of their mode (`gameMode` in the state is the local player's). A `spectator: true` (`AbstractClientPlayer.isSpectator()`, from the tab-list entry) would let the body hide every spectator, not only the names in `RESIDENT_UNSEEN_PLAYERS`.
- **Attack cooldown.** `attackStrength` (`getAttackStrengthScale(0.5f)`) and `attackDelayTicks` (`getCurrentItemAttackStrengthDelay()`) in the summary, so swings land at full strength with modded weapons too, instead of from a vanilla material table.
- **Who hurt me.** The last damage source (`getLastDamageSource()`: type, attacker and direct entity ids, age in ticks) so a fight starts against the mob that hit, not the nearest hostile, and a fall or fire is not blamed on a mob.
- **Aim and sight.** Each entity's bounding-box height, `hurtTime` (whether a hit registered) and a line-of-sight flag (`player.hasLineOfSight(e)`), so a fight aims at the real middle, counts real hits and can tell a skeleton behind cover.
